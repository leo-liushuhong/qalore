Testing Engineering Framework

qalore
全栈测试工程师网关

让 AI 成为真正的测试工程师 —— 拥有持久记忆、遵守工程规范、熟悉项目上下文，自主判断如何工作，而不是被流水线驱赶。

Why · 设计动机

三个矛盾，一个答案

AI 能读懂需求、能写用例、能执行测试，但它有三个与生俱来的缺陷，qalore 正是为补足它们而生。

1

没有持久记忆

每次会话从零开始，项目知识无法沉淀。qalore 用 story 把项目知识「物化」，跨会话、跨模型、跨 agent 协作。

2

规范容易漂移

口头约定会变、会忘、会自相矛盾。qalore 用 practices 把规范写成可机器校验的 spec，机器能判定的不靠 AI 自觉。

3

能力不可复用

换个项目，测试方法就推倒重来。qalore 用 capability 把「测试的思考方式」沉淀下来，与业务解耦，可迁移。

Design · 设计思想

双螺旋自迭代模型

qalore 内部有两条螺旋：一条承载业务，一条承载方法，它们通过「断言」完成碱基配对，持续自迭代。

业务螺旋
story（唯一业务知识库）
⇌
方法螺旋
practices + capability（纯 spec）
→
碱基配对
断言三层映射

分离

story 是唯一承载业务内容的地方；practices 与 capability 不出现任何业务词，只用占位符描述通用规则。

连接

业务逻辑断言（BL）→ 测试用例断言（TC）→ 执行结果，三层一一映射，信息流动不中断、不失真。

自迭代

审计闭环回馈质量改进；外部审计（audit）再检查 qalore 本身，双螺旋不断逼近更高质量。

一句话纲领：「只有 story 涉及业务内容，qalore + audit 完全是测试 + 企业 spec。」判断一条规范是否越界的唯一标准 —— 换一个被测项目，它还能用吗？
Method · 设计方法

Spec 而非 Workflow

qalore 不规定 AI 的每一个动作，而是划定边界、提供工具、注入上下文，把智力发挥空间留给 AI。

AI 是主体，框架是支撑

AI 像一名专业员工：有技能、守规范、懂背景。框架只给工具、设边界、供上下文。违反这条就是把员工变成流水线。

Capability = 思考哲学

能力的唯一职责是装备 AI 某个专业领域的思考方式。加步骤 ≠ 加能力，只有加思考维度才是。

Practices = 公司规范

划定边界防失控，不干涉边界内的智力发挥。规定「按功能点分节」，不规定「断言写什么」。

渐进式披露

按上下文流转切割，不按角色切割。index.json → 内容文件 → changelog，每层按需加载，流转不中断。

Landing · 落地方法

三层资产 + 机器校验

设计思想落成三套可维护的文件，再配上一台机器校验脚本，让「正确」可以被自动证明。

P

practices · 规范

通用规范、技术栈规范、schema 权威、机器契约（contracts.json）。写的是「按什么规矩测」。

C

capability · 能力

五个测试能力，各自封装一套思考方式。写的是「怎么思考着去测」。

S

story · 知识库

项目-模块两级目录，四类文件（业务逻辑/测试用例/代码逻辑/变更日志）。写的是「测什么」。

版本机制

机制作用
version = {日期}-v{n}practices 的版本号，与 changelog[0] 强一致
practices_min_version每个 capability 声明依赖的最低 practices 版本，网关路由前校验
变更四步写 changelog → 同步 version → 注册文件类型 → 同步 audit 依赖图
verify-contracts.py11 项契约校验，含「audit 依赖图对齐」——版本 gap 由机器暴露，不靠人工审查
Usage · 使用方法

五个能力，一条流水线

从「理解需求」到「审计一致性」，五个能力串起完整的测试工程闭环。

能力职责思考方式
qa-understand把需求/代码/设计稿转化为可测试断言三驱动认知 + 多源证据聚合
qa-functional-test以断言为输入，设计覆盖全面的测试用例用户影响优先 + 覆盖拓扑
qa-case-review对用例做多层质量检查，输出问题报告溯源式质量判断
qa-execution按断言规则在浏览器逐条执行，产出报告断言驱动执行 + 自动化不变式
qa-audit全量审计一致性，产出待修复清单机器校验 + 语义审计流水线
