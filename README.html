01 · Landscape 2026

2026 年，测试正在被重写

过去半年，几个信号同时出现，说明「Agentic Testing」已从概念进入成熟市场。

Gartner 2026 年发布「Agentic 软件质量保证平台」魔力象限，UiPath、Tricentis、SmartBear、LambdaTest 等厂商集体押注「AI QA Agent」。

认知转向

Google Cloud《AI Agent Trends 2026》：AI 不再是 copilot，而是目标驱动、能自主规划行动的 teammate。QA 战略从「执行用例」转向「风险智能」。

技术定型

Skill 与 MCP 分工清晰

Skill 承载「知识与 SOP」（大脑/剧本），MCP 承载「连接与执行」（手/接口）。950+ MCP server、agentskills.io 跨平台标准、MCP 进入 CNCF——基础设施已就绪。

但厂商都在做「黑盒平台」：把 AI 包装成一个替人测试的 SaaS。qalore 走的是另一条路——不封装能力，而是沉淀能力。方法论、规范、项目知识全部写成文件，模型只是执行者，机器负责校验。这正是 2026 年被验证的「Skill 路线」在测试领域的落地。

03 · Capability 1

测试意图理解与提炼 qa-understand

把任意信息源——需求文档、代码、数据库 schema、设计稿——转化为可测试的断言。这是整个链路的地基：断言错了，后面全错。

CORE COGNITION

三驱动认知框架

回答「为什么读、何时停、如何识别边界」的认知姿态，全程有效。

假设优先

读之前先假设「这个模块做什么、谁触发、影响什么」，读是验证和修正假设，不是从零积累。停止条件是：假设中所有已知交互都有了来源证据。

证据驱动

每条论断必须有来源。任何「我认为是这样的」都是待验证假设，不是断言。

模型驱动

每读一段，问——这证实还是推翻了假设的哪个部分？

边界驱动

每个系统交互都有两端。遇到边界判断另一端是否已知：已知则记录 [模块::功能点]，关键但未知则主动追踪，不关键则标注「链路断点」。

ADAPTERS

三类信息源适配器

按需加载，不预加载；多源顺序执行，最后统一综合。
适配器信息源写入目标粒度上限
text 文本PRD / 需求文档 / 官方文档 / 口述 / URL业务逻辑.md规则级
code 技术代码 demo / 接口设计 / DB schema / git 代码（支持 N 个仓库）代码逻辑.md设计期表级 → 产物期字段级
design 设计Figma 设计稿业务逻辑.md组件级
测试左移的两期模式：同一个技术适配器覆盖两个成熟度阶段——设计思路期（技术评审时，只有接口/DB 设计思路，产出契约级断言）→ 实际产物期（有 git 代码 / DB schema 后，下钻到字段级实现断言）。测试在代码写出之前就开始。
MULTI-SOURCE

多源聚合与置信度标注

文本 + 代码 + 设计的任意组合，逐源标注，冲突显式化。

每条断言带置信度标注，供下游用例设计和执行分流使用：

✓ 已确认 ✓部分代码确认 待代码确认 代码独立（单源） 代码独立,多源 ⚠️ 文本-代码冲突 ⚠️(代码) 多源代码冲突
冲突不掩盖：当文本说的和代码做的不一致，不强行合并，而是标注 ⚠️ 冲突，暂停让用户确认以哪个为准。这是「证伪式协作」的第一道关卡——发现矛盾，而不是假装一致。
04 · Capability 2

功能测试用例设计 qa-functional-test

以断言集合为输入，设计覆盖正向/边界/异常/上下游的用例，并产出可执行的测试产物。

COVERAGE TOPOLOGY

覆盖拓扑：断言是节点，用例是展开

禁止把断言 1:1 转译为用例。

每条断言先识别其变量维度，再沿维度拓扑展开：

六个变量维度

主体 / 客体 / 动作 / 约束 / 通道 / 场景

四个测试维度

正向 / 边界 / 异常 / 上下游

双通道入口

前端 UI + 后端 API 直调，缺一不可

用户影响优先：设计前先问一句——「如果这个模块今天在生产中出问题，用户最先感受到什么损失？」以答案定义 2-3 个优先场景，为它们设计多角度用例；高风险的 ⚠️ 和 待代码确认 断言额外追加高优先级用例。

05 · Capability 3

用例评审 qa-case-review

评审的目标不是找格式问题，而是回答一个问题：这批用例拿去执行，会漏掉什么、卡在哪里？

结构层

可执行吗

字段是否完整？每个触发性步骤是否有对应预期？每个 → 预期 是否有对应 → 断言？

覆盖层

该测的都测了吗

每个功能点是否覆盖正向/边界/异常/上下游四维度？每条断言是否有对应用例？「断言 × 变量组合」是否展开？双通道是否覆盖？

归因层

根源在哪一层

用例写法问题 → 设计层缺陷；断言没被设计进来 → 理解层遗漏。定位根因，而不是停在表象。

写 mock 五围栏审查：评审阶段对用例里的写 mock 声明逐条核对五道安全围栏——环境白名单 / 数据白名单（字段级）/ 可还原（快照）/ 已声明 / 待人类确认。五围栏齐全才标记「已确认」；围栏缺失即阻断。「副作用是否可接受」是「应不应该」问题，由人类拍板，AI 只做形式校验。
06 · Capability 4

自动化测试执行 qa-execution

读取用例里的断言规则，通过 Playwright 在真实浏览器里逐条执行，产出执行报告。断言是「可执行的规格」，不是给人读的文字。

ASSERTIONS

28 种断言类型，五类全覆盖

UI / Console / 视觉样式 / API / DB，全部走统一的可验证语法。
类别示例
UIelement-exists(.primary-btn) · element-count(.item, 5) · element-text(.title, "标题") · url-contains("/login")
Consoleconsole-error-contains("Uncaught TypeError")
视觉样式element-color(.title, "rgb(24,144,255)") · element-font-size(.title, 16) · element-border-radius(.card, 8)
APIapi-status(/api/*/list, 200) · api-field-value(/api/*/list, "total", 9)
DBdb-field-value(库, 表, ID, 字段, "值") · db-row-count(库, 表, 条件, 3)（psql 只读 SELECT）
双模式分流

验证模式 vs 校准模式

高置信度断言走验证模式（正常 pass/fail）；低置信度断言（待代码确认/⚠️）走校准模式——首次执行不判 FAIL，产出「校准差异报告」，按「推理失真 / 实现漂移 / 文档不完整」三分类归因。避免把「断言本身没写准」误判成「代码有 bug」。

无人值守

自动化五条不变式

幂等（只跑无副作用用例）· 范围声明（校验执行范围非空）· 只读安全（含写 mock 自动 SKIP）· 漂移保护（同一 TC 连续 FAIL ≥ 3 次标记「疑似断言漂移」）· 失败可见（报告落盘可拉取）。

待回写项：执行不只是跑用例，还持续发现「断言与实测不符」「端点漂移」等问题，写入【待回写项】清单——作为后续回写 story 的可追踪来源。执行本身也在反向修正知识库。
07 · Capability 5 + Audit Skill

审计 qa-audit · qalore-audit

qalore 最特别的能力：不是测业务，而是测自己。qa-audit（内建能力）做全量审计，独立 skill qalore-audit 做变更驱动定点审查——持续发现体系自身的漂移与不一致。

机器校验 · 11 项契约

能判定的不靠 AI 自觉

assert_seq 数据 / 断言类型数据 / assert_seq 副本语义 / 断言类型计数副本 / 计数字段 / ID 规则 / 版本一致性 / 依赖登记（prod 排除·秘密脱敏·写 mock 确认）/ 外部工具 / @档位合法性 / 依赖图对齐。脚本一跑，漂移立即暴露。

语义审计 · 19 步流水线

脚本判不了的，人工判断兜底

原子变更验证（跨模块成对改动）/ 示例即契约（文档示例 ↔ 真实数据）/ Changelog 真实性（「声称已修」↔「实际状态」）/ 跨模块引用一致性 / subagent 分层合规 / 环境可用性一致性 / 依赖一致性。

两套审计，分工明确：qa-audit（内建能力）做全量审计——19 步流水线 + 11 项机器校验；qalore-audit（独立 skill）做变更驱动定点审查——沿依赖图只查受影响下游，归入七类问题（合约不一致 / 传播遗漏 / 术语陈旧 / 机制模糊 / 结构破损 / 时序错误 / 分层越界）。两者共享版本锚点（机器强制对齐），不重复审计同一维度。
08 · Governance

治理层：Practices 规范与 Story 知识

五个能力是「怎么做」，治理层回答「按什么标准做、关于什么东西做」。这是 qalore 迭代最深、也最不可替代的部分。

Practices · 三层规则

规范像代码一样版本化

common（什么是好的产物）· tech-stacks（断言/用例/执行的格式与规则）· schemas（结构的权威定义）。每次变更带 YYYY-MM-DD-v{n} 版本号 + changelog，能力声明 practices_min_version 做版本兼容检查——规范漂移会被机器发现，而不是靠记忆。

Story · 知识三元组

每个模块三份文件

业务逻辑（需求说什么）· 代码逻辑（代码实际做什么）· 测试用例（如何验证）。断言级关联（assert_seq 全局序号）、跨模块上下游标签、跨会话持久化、断点可恢复。外加 changelog、评审记录、执行报告——知识持续累积，不因换模型而丢失。

方法论（能力）会随模型退化，规范（Practices）与知识（Story）永不退化。
09 · Double Helix

双螺旋：业务链 × 方法链，审计自迭代

qalore 不是单向流水线，而是两条知识链相互缠绕、通过「断言」配对、通过「审计」自迭代的闭环。

螺旋一 · 业务链

Story 是唯一业务知识库

业务逻辑 / 测试用例 / 代码逻辑 / 变更日志，按「项目 → 模块」组织。业务知识随测试持续沉淀，不因换模型而丢失。

螺旋二 · 方法链

qalore = Practices + Capability

纯测试 + 企业 spec，只承载测试方法、契约与哲学。严禁参杂业务内容——业务内容一旦流入，即破坏双螺旋分离。

10 · Why this path

为什么这条路是对的

Skill 路线被 2026 验证

当厂商在造「黑盒 AI 测试平台」时，业界同时验证了另一条路：Skills 击败 Prompts、Claude Code Skills 主导 2026、agentskills.io 跨平台标准。qalore 的「纯文本规范 + Skill 能力 + MCP 执行」架构，正好站在这条被验证的路线上。

约束驱动，而非角色驱动

「你是测试工程师」是模糊的角色扮演；「每条断言至少对应一条用例、每条用例有可观察预期、所有异常路径有覆盖」是可逐条验证的约束。qalore 把后者做成了机器可校验的规范——这是它区别于所有「提示词测试助手」的根本。

AI 扩展信息处理，人留下做判断。
qalore 让「判断的标准」可以被沉淀、被校验、被迁移。
